# SCPFS architecture decisions

Date: 2026-10-03 (Asia/Shanghai)

Additional user requirement: preserve existing remote file modification and access timestamps at nanosecond precision across SCP/cache transfers; explicit SetFileTime updates are honored. Existing-file payload commits retain the snapshot times, new files use cache-file times. SCP's second-resolution timestamps are completed by GNU touch for subsecond precision. Atomic temporary-file replacement cannot preserve Linux birthtime; this limit is documented.
Status: implementation, shared WinFsp frontend, native service lifecycle and production SCP runtime accepted for the tested scope on 2026-10-03. See `VALIDATION.md` for exact evidence and limits and `D:\work\fs\frontend\DESIGN.md` for the shared frontend boundary.

## Objective and confirmed basis

Provide a Windows mounted, read/write filesystem whose file payload uses the legacy SCP protocol. The user confirmed a Linux/GNU server and requested reuse of the `D:\work\memfs` framework to complete the project quickly. Luna reconnaissance identified memfs's C17/clang-cl/CMake WinFsp callback and dispatcher lifecycle as the reusable framework. Reuse those source patterns directly, including dispatcher stop reporting; adapt storage callbacks to the SCP backend. The user requires an EXE with only operating-system DLL dependencies. Reuse memfs's static WinFsp library and SYS-only embedded driver framework, with static libssh2/OpenSSL/zlib and the static CRT. The static compile path must not extract or load a third-party runtime DLL. Reuse an already compatible running driver; never stop or replace a loaded driver supporting existing volumes.

Initialize OpenSSL explicitly with `OPENSSL_INIT_NO_LOAD_CONFIG` before libssh2 or any other OpenSSL operation. A static OpenSSL library can otherwise read `OPENSSL_CONF` and load an external provider DLL. This product uses its statically linked default crypto implementation and ignores external OpenSSL configuration/provider activation; verify that an environment-supplied failing provider configuration cannot change a successful SSH probe. PE normal/delay import checks and real-process module inventories remain independent acceptance gates.

Hostname resolution must use built-in Windows DNSAPI rather than Winsock namespace-provider lookup. Actual production `getaddrinfo` loaded Bonjour's `mdnsNSP.dll` despite an OS-only PE import table. Numeric IPv4/IPv6 addresses are parsed directly; hostname A/AAAA results use Windows DNS client/cache/hosts behavior, an absolute DNS/TCP deadline and lifetime-safe asynchronous cancellation. Keep the original configured hostname for known-host verification. This boundary adds only the operating-system `Dnsapi.dll` and must not modify system providers. Both hostname-fixture and production module inventories are release gates.

Both products link the static C17 `fs_frontend` library. It owns all 31 WinFsp operation dispatch wrappers, mount/dispatcher lifetime, common SCM hosting, protected logs and native installation/uninstallation. Existing storage callbacks and per-product file-context semantics remain unchanged. Native installation captures absolute credential paths and the installing user's SID, configures delayed automatic LocalSystem startup plus bounded recovery, and starts immediately. Identical installation is idempotent; another configuration is rejected without rewriting it. Uninstall verifies the registered executable and removes only that named user-mode service. The running shared driver and unrelated mounts are preserved.

## Lead architecture decision

The compact Luna briefing escalated the new cache/writeback boundary for a data integrity review. Accept an initial whole-file cache design with explicit consistency limits. SCP has no random-write, directory-query or compare-and-swap primitive. Files are downloaded with libssh2 SCP and edited in local cache; metadata/namespace operations use safely quoted GNU commands over the same authenticated SSH session. There is no SFTP fallback. Basic filesystem operations do not require Python; notification-backed read reuse uses the embedded Python 3 helper described in CACHE_ARCHITECTURE.md, without installing a daemon.

Linux names remain case-sensitive. The user subsequently made case sensitivity a mandatory requirement. Set `CaseSensitiveSearch=1` and `CasePreservedNames=1`, keep all namespace/cache comparisons exact, and require real mounted tests for distinct `Test.txt`/`test.txt` contents, enumeration, deletion independence and case-only rename. Reject Windows-unrepresentable components, traversal, alternate streams, control characters and symbolic links/special files. The configured root must be an existing absolute directory and the backend must validate its canonical path and operation ancestors. This is a mapping for a trusted remote account/root, not a security sandbox against an account concurrently replacing ancestors. Deny rename/delete of the mounted root.

A single filesystem instance serializes callbacks/backend access and grants at most one active cached handle per regular file in the initial implementation. WinFsp Cleanup marks the last user handle closed and releases a clean handle from the path guard even if the later Close callback is delayed by cached references; handles with unresolved dirty metadata/data continue to block another open. Multiple directory handles can be supported independently. This restriction is intentional and must be in README: applications requiring concurrent active handles to the same file may receive sharing violations. It avoids divergent per-handle snapshots. Reject directory rename/delete when it affects active descendant handles; reject replacement of an active destination. Successful file rename updates cached path/state. Preserve dirty content until successful commit; never reload over a dirty cache.

Existing regular-file Open must distinguish payload access from metadata-only access using WinFsp's granted access mask. A stat, attribute/time or delete-only context with none of `FILE_READ_DATA`, `FILE_WRITE_DATA`, `FILE_APPEND_DATA` or `FILE_EXECUTE` does not download or own a payload cache. Clean metadata-only contexts do not block path/cache guards while waiting for Cleanup; dirty metadata, deletion failure and unresolved inbox/recovery state still block. Do not admit a metadata-only mutation alongside another active payload context, or bypass unresolved dirty payload state. Metadata-only SetBasicInfo commits synchronously and returns backend failure; Create and payload-handle writeback remain unchanged. Payload callbacks defensively reject cache-less metadata contexts. The boundary preserves one active payload cache and avoids treating a delayed metadata/stat close as another file editor. Exact nanosecond SetFileTime followed by immediate delete must be repeatedly exercised without sleeps or test retries.

Because these cache-less contexts can survive a namespace change, successful rename/delete and command-input consumption must mark affected clean metadata peers stale, including directory descendants and replaced destinations. A stale context may expose its saved file-info snapshot but must reject remote metadata/rename/delete mutations and skip Cleanup/Close commits or inbox triggers. Before a rename, reject other active payload or unresolved contexts at the source as well as the destination. Do not retarget an old destination descriptor to the replacement object, and do not allow a stale pathname to modify a newly created file. This initial backend does not preserve a live mutable metadata descriptor across namespace changes; callers must reopen the new path. This bounded invalidation avoids introducing shared file-node storage or another payload cache.

Delete validation and the actual Cleanup deletion both check other active contexts. A Close/Cleanup command trigger from a clean metadata-only context encountering an active payload owner launches nothing and leaves submission to that owner's Close; it does not create a recovery latch that would block the owner, and the completed Cleanup prevents a later Close retry. Other active/unresolved conflicts are recorded as known-not-launched recovery failures before dispatch. Explicit Rename checks the source guard before even the same-path inbox branch, so it cannot report success for a conflicting skipped command. No deferred retry state is introduced. Successful synchronous metadata commit clears `modified_after_cleanup`; only truly clean metadata contexts can be invalidated.

The cache object is a per-open descriptor, so the volume must set `UmFileContextIsUserContext2=1`. WinFsp's default context is a file node that must remain identical across opens while the kernel retains that node (`inc/winfsp/winfsp.h`, interface documentation). Reusing that default with newly allocated SCPFS handles caused intermittent invalid-handle failures after close/reopen and rename in the real mount test. Select descriptor semantics rather than redesigning the cache as shared file nodes; repeat close/reopen/rename/delete and inbox submissions after the correction.

The supported initial implementation uses exactly one WinFsp dispatcher worker. `scpfs_start(..., 0)` selects one worker; counts greater than one are rejected. Luna's focused investigation identified a real close-to-delete failure in the active-cache guard: a clean descriptor still had `cleaned_up=0` when the next Open ran. Local WinFsp source posts Cleanup and Create/Open to the queue tail, but its default affinity-scaled workers can dequeue those requests and acquire the SCPFS lock in a different order (`src/sys/cleanup.c`, `src/sys/create.c`, `src/sys/ioq.c`, `src/dll/fs.c`). The lead selected one worker to preserve callback processing order while retaining strict single-cache and conflict protections. The backend already serializes network access. Do not substitute a sleep/retry or allow divergent parallel write caches. Verify repeated immediate close/read/reopen/delete without a delay and repeat the full mount suite before release.

Commit on explicit Flush and on Cleanup/Close as the framework permits. Cleanup runs for clean and read-only handles (`PostCleanupWhenModifiedOnly=0`) because it represents the last user close and may trigger the exact `.in.txt` inbox protocol; Close is a fallback only when Cleanup never ran. Upload to a cryptographically unpredictable unique sibling name, preserving the existing mode; after the complete SCP protocol exchange and acknowledgement, compare the observed destination size, nanosecond mtime, mode, device and inode with the original snapshot before moving the temporary file into place. A new destination must still be absent. Return a failure when an observed conflict exists. This is best-effort conflict detection; concurrent external writers can race the comparison/rename. Supported operation assumes this mount is the only writer of its remote tree. Do not claim distributed CAS, coherent multi-client access or crash-durable remote fsync.

The literal basename `.in.txt` is reserved for remote shell-command submissions. After Cleanup commits successfully, the backend atomically claims and runs it once; rename into that exact name commits before the rename and submits after the path changes. Ordinary Flush and directory traversal never trigger commands. The handle records attempted/consumed/unknown state to prevent automatic replay, and failed or uncertain submissions keep their local cache and recovery manifest. This is intentional execution of user-supplied shell text under the authenticated account and is not a shell sandbox; see `docs/COMMAND_PROTOCOL.md` for the full limits and behavior.

All callback failures that can be returned must return an NTSTATUS. The latest user cache instruction is to use `%TMP%`, superseding the briefly proposed M: drive. Create a unique session subdirectory under `%TMP%\scpfs`; never clean another session's or user-owned files. Cleanup/Close cannot return an error: log a clear path and error, retain the failed dirty cache plus recovery metadata, and expose the supported recovery procedure. Flush failure must not mark the node clean. Successful unlink removes an unnecessary cache; failed deletion is logged and must not silently invalidate live state. Cache teardown follows dispatcher shutdown and worker completion.

Host-key verification using an explicitly supplied OpenSSH known_hosts file precedes authentication; the local mounted security descriptor grants access to the launching TokenUser SID and SYSTEM, with explicit owner/group, rather than sharing the authenticated remote account with Everyone; unknown/mismatched keys fail closed. Authentication is public-key-only with no password or keyboard-interactive fallback. An explicit identity overrides the default home/.ssh/id_ed25519; absence of that file fails clearly. A private-key decryption passphrase, if supported, is not a remote password authentication method. Every connection/channel operation has finite timeouts. SSH output is bounded and NUL-framed. Command arguments are quoted individually; never parse locale-dependent ls output. Upload names must not be predictable or overwrite an existing unrelated temporary file. Disconnect/timeout returns errors without blind replay of mutations.

The command timeout defaults to 30 seconds and is capped at 540000 ms. The volume uses WinFsp's maximum 600000 ms IRP timeout to leave time for command termination and result publication. Extreme configured operation timeouts and adverse network latency are not runtime-proven within that overall driver budget; preserve recovery state if a callback cannot complete.

## Runtime gates and unknowns

The session read cache and server notification extension is governed by [CACHE_ARCHITECTURE.md](CACHE_ARCHITECTURE.md). Read caching stays enabled; the final user-selected default capacity is zero/unlimited, with positive MiB values applying payload LRU limits. Separate immutable reusable copies never replace per-open writable descriptors or recovery files. The monitor uses a second SSH session pinned to the main backend's canonical root, inotify coverage acknowledgements and epoch barriers; external changes invalidate clean reads eventually. This does not change the single-writer/conflict boundaries of mutation operations.

Required: Debug/Release clang-cl build; CLI validation; known-host mismatch/unknown-host rejection; real SCP download/upload and GNU metadata operations on an isolated loopback WSL sshd; actual Windows mount CRUD/random read/write/truncation/rename/delete/Unicode and quoting paths; conflict rejection and dirty-cache preservation where fault injection permits; clean Ctrl+C/dispatcher teardown. Compilation and backend tests do not establish mount acceptance. Current evidence must be recorded separately from these requirements. Network fault durability, performance, large-file throughput, hostile concurrent ancestor changes and multi-client coherence are outside initial acceptance and must remain explicit limitations.
